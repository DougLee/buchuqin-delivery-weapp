# 配送端白天店与夜宵店双向入口设计

设计稿：`../designs/day-night-workspace-switch.html`。已按确认设计实现双向切换。用户确认的最终权限：**仅正式楼长，实习楼长不显示**。

## 入口与视觉

两个首页将身份信息、经营状态和切换入口合成一条顶部栏：左侧品牌/夜宵经营台及楼栋（白天为校区），右侧经营状态与「切换夜宵店 / 切换白天店」。按钮紧靠内容区右缘，配太阳/月亮及双向箭头，触摸范围至少44px。微信构建在状态栏下额外预留44px原生导航区域，避免新位置与右上角胶囊重叠；真机效果仍需原生验收。

紧凑版调整：去掉独立切换卡片及重复的店铺标签，经营状态和按钮以内联模式放进现有身份栏。标题与楼栋保留信息层级，长校区名省略，右侧按钮不压缩、不换行。两套首页删除不对应实际订单阶段的装饰流程线，主卡保留问候和真实待办数量；夜宵月光轨道缩小、降低对比度。营业状态在顶部展示时，夜宵主卡隐藏重复徽章；无切换资格时主卡仍显示状态。

白天使用浅底、白卡、绿色文字和描边；夜宵沿用深翡翠、暖金描边和柔和金色按钮。切换条低于开店/打烊等业务主按钮的视觉优先级。原白天首页 NightSlotCard 合并为新切换条，避免重复入口及押金信息堆叠。底部继续使用各自四个Tab；「我的」经营分组保留备用入口。

## 产品规则建议

1. 切换只改变当前工作台，不调用开店、打烊、上下线接口；不更换用户身份。点击后进入目标首页，无二次确认，网络跳转期间防重复点击。
2. 仅已绑定夜宵店的正式楼长展示双向入口。实习楼长、全职/兼职骑手、未绑定夜宵店的正式楼长均不显示。后端 `business-context` 新增 `staffId/staffRole/canSwitchWorkspace`，客户端同时核验真实角色与绑定资格。资格失效清理手动选择，既有营业权限继续由原业务接口校验。
3. 非营业时段可进入夜宵工作台备货、看商品/库存/收入；开启营业仍由服务端校验。夜间可进入白天工作台查看和完成已有任务，新任务承接仍遵守原营业规则。
4. 选择按员工账号保存，切换订单、收入、我的及刷新时保持同一工作台。已有有效选择优先；首次进入无选择时用服务端时段决定默认工作台；换账号隔离，退出登录清除。
5. 切换保留已接订单；跨工作台新单继续按原轮询/订阅通知规则提醒，手动选择后轮询不强制抢走当前页面。

## 已实现的调整

- `utils/nightMode.ts`：区分服务端营业时段与用户当前工作台。`dayTabGuard`、`nightTabGuard`、`syncWorkspaceMode` 应统一读取工作台选择，避免手动回白天后被轮询跳回夜宵。跳转失败时保留原选择，恢复按钮状态。
- `components/WorkspaceSwitch.vue`、两侧首页：复用切换条组件，替换并移除旧 NightSlotCard，主动选择后进入目标首页。
- `pages/profile/index.vue`：主题和TabBar跟随当前工作台，不能继续只看服务端 `ctx.mode`，否则夜间选择白天后「我的」仍变夜宵主题。
- 登录/登出及后台换楼长：清理或隔离工作台选择；前台刷新资格，并保留网络失败前的有效选择。

## 实现验收

双向切换→订单→收入→我的→返回，主题、Tab和数据源一致；夜宵时段手动选择白天，跨轮询和刷新不被跳回；白天进入夜宵准备页可备货但不能绕过开店校验；换账号/解绑后不沿用原楼长选择；切换不改变店铺营业状态、员工在线状态或订单状态。

- `npm run test:workspace-switch`：9项权限、账户隔离、轮询、导航回滚及重复点击测试。
- API `node scripts/test-night-stock.mjs --skip-push --all-night`：独立schema 33项通过，含4种角色及未绑定情况。
- API `node scripts/test-night-workspace-http.mjs`：使用本机3150与独立预览schema验证真实角色返回；已绑定实习楼长明确返回不允许切换。
- 浏览器逐个切换上述非授权角色，均未渲染切换条，且旧的手动选择被清除；实习楼长本机角色标记改成正式楼长也不能展示入口。

发布时先更新API，再更新配送端；本功能无数据库结构迁移。旧API缺少新资格字段时入口保持隐藏。微信右上角胶囊的真机视觉及微信登录仍需开发者工具/真机验收。

验证记录：曾误将旧 `night.spec.ts` 直接运行到测试库默认schema，因缺少字段在夹具初始化阶段失败。其业务夹具由afterAll清理；本次唯一遗留孤立分类已按精确ID、校区ID及无关联商品条件清理。随后通过上面的隔离schema脚本完成全部33项验证，未涉及生产。
