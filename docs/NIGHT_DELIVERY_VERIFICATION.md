# 夜宵配送端 M2 验证记录

工作分支：`feature/night-store`。API 与配送端代码位于同级 worktree。

## 本轮补齐

- 服务端 business-context 决定白天、夜宵、休息三态；工作台、任务、收入三个 Tab 使用统一业务容器。
- 跨时段白天订单使用独立收尾列表，不恢复整套白天工作台；夜宵历史订单保持独立入口。
- 押金档位可选；服务端验证目标档和差额；支付单号在拉起支付前持久化，支付未知时保留查单入口。
- 进货确认展示入库后的货值与额度；支持从校区商品池首次选品；全店库存参与额度检查，同店备货使用数据库锁串行执行。
- 备货 requestId 复用原单，避免网络重试重复入库。
- 夜宵送达须提交照片，事务内保存凭证、完成订单和处理预计佣金；售后进行中不提前转待结算。
- 新楼长不可通过配送端查询旧经营者订单及备货记录，商品上架检查后台停售与库存。

## 验证方式

1. 配送端 `vue-tsc --noEmit`。
2. 配送端微信小程序编译（使用本机预览 AppID，不调用支付）。
3. API `nest build`。
4. `night-rider.behavior.spec.ts`：内存替身测试，不连接数据库。覆盖营业模式、无资格员工、全店货值、防重复入库、押金档位和送达完成。
5. 本机 H5 夹具预览：工作台/押金/进货；确认白天无夜宵主界面、夜间无白天主界面，以及320/375/414px进货页无水平溢出。

## 部署前仍需验证

- 新增 migration `20261106030000_night_stock_request_id` 尚未应用任何业务数据库；API上线前必须执行迁移。
- 微信真机交押金、支付回调与主动查单、实际图片上传和订阅通知仍需在测试环境联调。
- 未执行生产部署、生产数据操作和 Git commit。
- 当前 worktree 原有架构仍使用 NightOrder，与此前讨论的统一 Order 方向不同；本轮未执行订单模型迁移。
- 库存货值沿用当前分支实时售价口径；批次/效期/退货与退出清算的待定设计未扩展。
- 原有品牌配置测试断言与内置小满AppID/名称不一致，需单独校准；本轮未修改品牌构建配置。
